# ADR-011 — Design system: Carbon (web responsive)

**Status:** ACCEPTED — signed off by Agentic Designer - RP, 2026-08-27
**Date:** 2026-08-26 (proposed) · 2026-08-27 (accepted)
**Evidence:** ART-002 (`artifacts/design-system-selection/…__v2/`)

Accepted 2026-08-27. The autonomy ladder puts research-synthesizer conclusions at
suggest-only and never graduates them, so this needed a human signature — which it now has.

**Added at acceptance:** Carbon's MCP server source is NOT published. Its repo holds 28 files
and zero runnable source — skills, llms.txt, a packaged extension, terms. Unlike shadcn, it
cannot be self-hosted. Early access is the only route to the running server, and it remains a
reference point rather than a dependency: the skills, the 157 Code Connect files and the
Apache-2.0 component source are all public already.

## Context

Platform scope was settled on 2026-08-26: **web responsive only, for now.** That
resolves the condition ART-002's verdict hung on — Carbon's single largest cost was
having no native mobile implementation, and web-only removes it.

## Decision (proposed)

Adopt **Carbon Design System** as CoForge's base for web.

It is the only candidate of nine that closes all three surfaces first-party:

| Surface | Carbon | Field |
|---|---|---|
| Claude Code | official MCP + `llms.txt` | 2 others have MCP |
| **Figma** | kit + **157 Code Connect artifacts** | **every other candidate: zero** |
| GitHub | Apache-2.0, pushed same day | several comparable |

Code Connect is the deciding factor. It is what makes a Figma component and a code
component the same object rather than two things that resemble each other. Without it,
ADR-001's inversion has no enforcement at the component layer and drift becomes
something a human must notice — the failure mode this system exists to remove.

## Corrections to the evidence, recorded

Three errors in my own benchmark, each found by verifying rather than re-reading:

1. **"254 Code Connect files" was wrong.** Verified count: **157** (2 `figma.config.json`,
   86 `.figma.tsx`, 69 `.figma.ts/js`). A double-counting regex.
2. **v1 never checked the Figma surface at all** and still called itself a benchmark.
   Closing that gap changed the verdict. Recorded as ART-002; ART-001 superseded.
3. **The MCP pillar is weaker than v2 implied** — see below.

## The MCP caveat — material, found after the verdict

Verified from IBM's own documentation on 2026-08-26:

- **Carbon MCP is Public Preview**, not general availability.
- **Access is gated for non-IBMers.** "Non-IBMers can request access using the link
  below — Early Access Sign-up Form." We would have to request and be granted access.
- **Its four tools are documentation search, not a component API.** `docs_search`,
  `code_search`, `get_charts`, `labs_search` — semantic search across docs and code
  examples. There is no tool returning a structured component contract.

The third point matters most architecturally. Carbon's MCP will not hand us
`component-index.json`. **We still generate the index ourselves** from Carbon's
packages, and Gate B still enforces against our copy. Carbon's MCP is a research aid
for agents, not the downstream source of truth.

This does not overturn the decision — Code Connect, `llms.txt`, licence and maintenance
are all unaffected and all first-party. But "Carbon has an MCP server" was doing more
work in the v2 scorecard than it can actually carry, and that is now on the record.

## Consequence: the DS fork moves RED → GREEN at Build Stage 2

Currently RED — `screen-producer` is wireframe-only. Adopting a system that already
exists in code means that once Carbon is installed and the index generated, the fork
becomes **GREEN**: screen-producer targets a real component library via Claude Code +
Figma MCP + Code Connect.

That is a large schedule change. Building a design system from scratch would have kept
`screen-producer` blocked through Build Stage 2 and most of 3.

## What we still build ourselves

Adopting Carbon does not remove the system layer. It changes what fills it:

| Layer | Source |
|---|---|
| `tokens/tokens.json` | Carbon themes → DTCG, then ADR-001 inversion into Figma |
| `component-index.json` | **generated by us** from Carbon packages — Carbon's MCP cannot supply it |
| `components/<Name>.md` | ours — CoForge intent and *when not to use*, not IBM's |
| `foundations/brand.md` | ours — brand-director, suggest-only, still blocked on brand inputs |
| `llms.txt` | generated from our index, as now |

## Accepted costs

1. **Strong IBM visual identity.** Carbon looks like IBM. Theming for a client means
   overriding an opinionated design language, not filling a neutral one. Whether that is
   acceptable is a brand decision, not a technical one — it belongs to brand-director.
2. **Apache-2.0, not MIT.** Commercially fine; carries patent and attribution clauses
   MIT does not. Needs client legal awareness.
3. **Low adoption** — 162k npm/week vs MUI 10.3M. Smaller community. Offset: IBM
   maintained, pushed same day.
4. **MCP is preview and gated** — see above.

## Rejected, and why

- **shadcn/ui** — highest adoption in the field (122k stars, 8.4M CLI installs/week) and
  structurally wrong for us. Copy-paste distribution means no upstream contract to index
  against, and `component-index.json` is what Gate B reads. Rejected on architecture, not
  quality.
- **HeroUI** — first-party MCP covering web *and* native, Apache-2.0, active. Zero Code
  Connect. **Reopen immediately if native mobile returns to scope.**
- **Ant Design / MUI / Mantine / Chakra** — strong libraries, zero Code Connect.
- **Material 3** — best native coverage in the field, `llms.txt` 404. No agent affordances.
- **Fluent 2** — real Swift + Compose, licence `NOASSERTION`. Blocked on legal, not merit.
- **Radix Themes** — 137 days without a push; the only stale candidate.

## Open before this can be Accepted

1. **What CoForge actually is** — still unanswered. It does not change the technical
   verdict but it governs brand, and whether IBM's identity can be overridden at all.
2. Request Carbon MCP early access, or accept working without it.
3. Confirm Apache-2.0 is acceptable to the client.
