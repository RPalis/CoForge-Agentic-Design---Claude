# ADR-021 — The dataviz layer: chart marks are not components

**Status:** ACCEPTED — Gate A, human decision recorded 2026-09-03
**Date:** 2026-09-03 (accepted 2026-09-03)
**Supersedes:** nothing. **Amends:** the first prohibition's scope; ADR-012's two levels.

## Context

CLAUDE.md's first prohibition is *"Never create a component that is not in
`design-system/component-index.json`."* It was written to stop off-system product
UI — invented buttons, rogue inputs that drift from the system.

Building a coverage dashboard raised a question the rule never anticipated: does it
govern **chart internals** — a dot in a dot matrix, a bar segment, a matrix cell?
Under the current reading it does, which means a heatmap cell requires a
`component-spec`, human approval and an ADR before it may be drawn.

Two findings made the question urgent rather than academic.

**`cf-chart-palette` cannot distinguish its own categories (C-036).** The registered
L1 primitive — `status: stable`, the only sanctioned way to colour a chart here —
uses `blue.60 · teal.60 · purple.60 · magenta.60`: four hues at one step on a Carbon
mirror where every hue family shares a single lightness ladder. Measured separation
is under 0.4%; worst-case pairwise contrast between any two hue families at the same
step, across all twelve, is **1.055:1** against a 3:1 floor.

**We inherited Carbon's components and Carbon's tokens, but not Carbon's charts.**
Of the 208 L2 entries the adapter ingested from `@carbon/react@1.115.0`, **zero** are
chart components — IBM ships those as a separate package, `@carbon/charts`, with its
own dedicated visualization tokens. Our token file has eight top-level groups and
none of them is dataviz. `cf-chart-palette` was improvised locally to fill that hole,
from the only colours available.

The broken palette is not a mistake inside the layer. It is the symptom of the layer
being missing.

## Evidence

Every design system examined draws the same line, and none was consulted by the
others:

| System | Treatment |
|---|---|
| IBM Carbon | separate package — `@carbon/charts`, with its own tokens |
| Adobe Spectrum | separate library — `react-spectrum-charts`; dataviz colour is its own token page |
| Shopify Polaris | separate package — `polaris-viz`, distinct from `polaris-react` |
| GitHub Primer | guidance only, filed under *UI Patterns*, not *Components* |
| USWDS | *"The data visualizations components are guidance-only and do not include any Component Code."* |
| GOV.UK Analysis Function | guidance plus an accessibility checklist; governed as WCAG obligation |
| Atlassian | separate chart token set, explicitly apart from UI colour foundations |

Three patterns, one line: a separate package, guidance with no shipped code, or
nothing at all. **No system registers a chart mark the way it registers a button.**

The reasons are structural to what a chart is, not particular to any one system:
brand colours chosen for buttons are not categorical colours; marks are generated by
a plotting grammar rather than hand-assembled from primitives; and the failure modes
are drift and inaccessibility, not unauthorised widgets.

## Decision

**A third governed layer exists between the foundations and product components.**

| Layer | Holds | Governed by | Gate |
|---|---|---|---|
| **Foundations** | tokens, `brand.md` | token-keeper; frozen without a release | A |
| **Dataviz** | chart marks and chart anatomy | the encoding contract below | **B only** |
| **Components** | product UI | the membrane — spec → approval → ADR → index | A |

**The dividing rule.** If it is drawn by the chart's own rendering logic — a mark, a
legend, a tooltip, an axis label — it is chart anatomy and belongs to the dataviz
layer. If it is a separate element a person clicks, or reads as a number — a KPI
tile, a filter control, a data table — it is an ordinary UI component and the
membrane applies unchanged. Primer and USWDS reached this rule independently; Carbon
confirms the KPI half directly, since `Tile` is a plain UI component and is not in
`@carbon/charts`.

**The first prohibition is unchanged in force and narrowed in scope.** It governs
components. It never governed chart marks; we had simply never had to say so.

### What governs the dataviz layer instead

1. **A dataviz token group**, parallel to the UI colour tokens rather than descended
   from them — categorical, sequential and diverging ramps validated for perceptual
   distinctness on our own grounds. This is the fix for C-036 and is what Atlassian
   and Spectrum both did. Owner: token-keeper.
2. **A written encoding contract with numbers, not adjectives**, after Primer:
   **3:1 for marks, 4.5:1 for axis text**, colour never the sole channel (WCAG 1.4.1,
   Level A — legally binding for public-sector work and not optional here), and
   mark-count ceilings per chart type.
3. **A sanctioned chart-type vocabulary**, checked at Gate B as *"is this an approved
   chart type for this data shape"* rather than *"is this an approved component."*
4. **Adversarial real-screen validation.** This is the counter-case's answer and it is
   not optional. The documented failure of splitting governance is not incompatible
   chart styles — it is drift that nobody catches because nobody inspects the
   assembled screen. `design-critic` already performs exactly this pass.

### Consequences

- `cf-unit-cell` (ART-017) is **chart anatomy**. It does not need promotion and
  should not have a `component-index` entry. The specification stays as documentation
  of the encoding.
- `cf-chip`, `cf-nav-rail`, `cf-detail-panel` (ART-018/019/020) remain **components**.
  The membrane applies to all three, unchanged.
- **C-038 is descoped, not solved.** The Carbon adapter still destroys any authored L2
  entry, so the RED exit condition remains unreachable — but a dashboard no longer
  needs L2 to be built, so that deadlock stops blocking L1 work. It still blocks
  Build Stage 3.
- `cf-chart-palette` should be marked **defective** rather than left `status: stable`.
  Its replacement belongs to the new dataviz token group.
- The exemption covers chart marks and their anatomy. It does **not** cover anything
  that merely appears on a dashboard: a bespoke cross-filtering brush or a custom
  comparison widget is product UI and returns to the membrane.

## Alternatives rejected

**Fold chart marks into the component index.** Rejected: no serious system does it,
and it would require an ADR per mark type — the membrane would become theatre, which
is the coverage illusion this repository exists to remove.

**Leave the dataviz layer ungoverned.** Rejected on the counter-case. Drift is the
real documented failure and prose guidance does not catch it. Hence items 2–4 above.

## Open

- Does `cf-chip` cross the line? It is a separate element read as a label, so under
  the rule it is a component — but a tier chip inside a matrix cell is arguable.
  Ruled here as a component; flagged as the closest call in this ADR.
- No check enforces the encoding contract yet. Until one exists, item 2 is prose, and
  prose is the weakest enforcement layer this repository has.
